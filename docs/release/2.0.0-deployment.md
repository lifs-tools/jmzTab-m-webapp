# 2.0.0 deployment and rollout

Prepared, not executed: nothing here has been published, merged or deployed. The project lead or ops carry it out (spec §5.7 of the SPA design, §5.9 of the version engines design). The patches below were computed against the current files of `docker-recipes-external` (commit `e926dba`) and `lipidcompass-ansible` (commit `0828e90`), read-only checkouts, on 2026-10-30. The `-dev` compose file already runs `mztab-validator-webapp:2.0.0-SNAPSHOT` (the earlier patch 1 is merged).

## What changes

2.0.0 splits the validator into three services (design `docs/superpowers/specs/2026-10-30-mztabm-version-engines-design.md`):

| Service | Image | Port | Memory limit | `/mztabvalidator-dev` | `/mztabvalidator` (production) |
|---|---|---|---|---|---|
| `mztabvalidator…` (webapp) | `lifs/mztab-validator-webapp` | 8083 | 1024M | `2.0.0-SNAPSHOT` | `2.0.0` |
| `mztab-engine-2-0` | `lifs/mztab-validator-engine-2.0` | 8084 | 2048M | `2.0.0-SNAPSHOT` | `2.0.0` (jmzTab-m 1.0.8) |
| `mztab-engine-2-1` | `lifs/mztab-validator-engine-2.1` | 8085 | 2048M | `2.0.0-SNAPSHOT` (jmzTab-m 2.1.0-SNAPSHOT) | — |

- The engines are attached to the stack's own `engines` network only: no Traefik labels, no published ports, no volume. The webapp joins both `proxy` and `engines` and finds the engines by service name.
- The `engines` network is not `internal: true`, because the engines need outbound HTTPS to the EBI OLS for semantic validation.
- Engines have no authentication; they must not be reachable from `proxy`.
- Production runs the 2.0 engine only. A 2.1 file there gets one error message that links to `/mztabvalidator-dev/` (`engines.unavailable-hint-url`).
- LipidCompass stays on 1.0.x until it opts in; its engines come with that opt-in.

## Rollout order

1. **Release jmzTab-m 1.0.8** (project lead) from the `1.0.x` branch of jmzTab-m. It contains only changes already merged on `1.0.x` (message suggestions, rule ids and locations). Then set `jmztabm20.version` to `1.0.8` in this repository's `pom.xml` on `feat/validator-spa`. Until then a release build fails by design (`requireReleaseDeps`, see `docs/self-hosting/building.md#releases`).
2. **Publish the snapshot images.** Trigger the `workflow_dispatch` of `.github/workflows/maven.yml` on branch `feat/validator-spa` (GitHub Actions, "Run workflow", branch `feat/validator-spa`). It pushes, with the version tag only (never `latest`):
   - `docker.lifs-tools.org/lifs/mztab-validator-webapp:2.0.0-SNAPSHOT`;
   - `docker.lifs-tools.org/lifs/mztab-validator-engine-2.0:2.0.0-SNAPSHOT`;
   - `docker.lifs-tools.org/lifs/mztab-validator-engine-2.1:2.0.0-SNAPSHOT`.
3. **-dev first.** Merge patch 1 and redeploy the `mztabvalidator-dev` stack (`docker stack deploy`), so that the two engine services are created next to the webapp. Check:
   - `https://apps.lifs-tools.org/mztabvalidator-dev/actuator/health` shows `components.engines.components.engine-2-0` and `engine-2-1` with `"status":"UP"`;
   - the About page lists both engines with their jmzTab-m versions;
   - a 2.0 and a 2.1 file validate (form and `POST /rest/v2/validatePlain`);
   - `docker service scale mztabvalidator-dev_mztab-engine-2-1=0` makes 2.1 files fail with "The mzTab-M 2.1 validator is temporarily unavailable. Please try again later." while 2.0 keeps working; scale it back to 1.
4. **Parity and memory check on `/mztabvalidator-dev`.** Work through `docs/superpowers/plans/2026-10-23-validator-spa-m1-parity.md` with the real files of the standalone design §3.3, including the 32 MB file with the 846 × 1,990 table and LCS-00050 with semantic validation. Watch `docker stats` for the webapp (limit 1024M) and the 2.0 engine (limit 2048M); raise a limit in both patches if a container gets close to it. Only a complete checklist allows the next step.
5. **Release 2.0.0** (project lead): merge `feat/validator-spa` into `master`, release with the `release` profile and without the 2.1 engine:

   ```sh
   ./mvnw -B -Prelease -DskipSnapshotEngines …
   ```

   `-DskipSnapshotEngines` is a bare flag (`=false` leaves the 2.1 engine out as well; to build it, leave the property out). The master push of the release version publishes `lifs/mztab-validator-webapp:2.0.0` and `lifs/mztab-validator-engine-2.0:2.0.0` (and `latest`); the workflow leaves out the 2.1 engine for versions without `-SNAPSHOT`. Check that both images exist before the next step.
6. **Production.** Merge patch 2 (webapp `2.0.0`, the new `mztab-engine-2-0` service, `replicas: 1`, the hint URL, 1024M) and redeploy the `mztabvalidator` stack. Keep `replicas: 1`: results are local to an instance. Check `/mztabvalidator/actuator/health` (`engine-2-0` `UP`, no `engine-2-1`), and that a 2.1 file gets the message with the link to `/mztabvalidator-dev/`.
7. **LipidCompass.** Merge patch 3 (volume only).

## Environment check

- **Webapp, -dev:** `ENGINES_MZTABM_0_LINE`/`_URL` and `ENGINES_MZTABM_1_LINE`/`_URL` configure both engines. Setting index 0 and 1 replaces the built-in default list (one 2.0 engine at `http://mztab-engine-2-0:8084`) as a whole. Quote `"2.0"` and `"2.1"`: unquoted, YAML reads them as numbers.
- **Webapp, production:** the built-in default (one 2.0 engine at `http://mztab-engine-2-0:8084`) matches the service name, so only `ENGINES_UNAVAILABLE_HINT_URL` is set. Spring Boot binds it to `engines.unavailable-hint-url`, as it does the canonical form `ENGINES_UNAVAILABLEHINTURL`; both were checked against the 2.0.0-SNAPSHOT image.
- **Unchanged:** `storage.location` defaults to `${java.io.tmpdir}/upload-dir` (`/tmp/upload-dir` in the container), where both public stacks mount their volume. The other new optional settings (`storage.max-total-bytes`, `sections.cache.max-bytes`, `validation.custom-mappings.enabled`, `rest.synchronous.max-concurrent`, `rest.synchronous.wait`, `matomo.tracker-base`, `engines.connect-timeout`, `engines.job-timeout`) have defaults; see `docs/self-hosting/configuration.md`.
- **Engines:** no environment needed. They listen on 8084 and 8085, run at most one job per processor at once (`engine.max-concurrent-jobs`) and use the EBI OLS (`engine.ols.*`).
- **Memory:** parsing moves from the webapp to the engines. The webapp's limit goes from 2048M to 1024M, each engine gets 2048M. All images start the JVM with `-XX:MaxRAMPercentage=75` (Jib `jvmFlags`), so the heap follows the limit (about 768 MB and 1.5 GB). A compose `entrypoint:` override replaces this flag; add it there if one is used. Confirm the values in step 4.
- **Placement:** the engines may run on any swarm node; the webapp stays on the node that holds its bind-mounted volume, as today.

## Rollback

- **Webapp and engines together.** Set the webapp image back to the 1.0.x tag (production `1.0.28` and `replicas: 2`; -dev `1.0.30-SNAPSHOT`) and remove the `mztab-engine-*` services and the `engines` network again (revert the patch). A 1.0.x webapp does not use the engines.
- **Rolling back loses all stored 2.0.0 results:** 1.0.x calls `storageService.deleteAll()` on startup, which wipes the whole storage volume. Result links shared during the 2.0.0 period stop working.
- **The 2.1 engine alone (-dev).** Scaling `mztab-engine-2-1` to 0 is safe: 2.1 files fail with the unavailable message, everything else works. To remove it for longer, also drop `ENGINES_MZTABM_1_*` from the webapp, so that 2.1 files get the "not supported" message instead.
- **An engine image alone.** The webapp and the engines are released together; roll back an engine only to the image of the same webapp version.

## Later

- jmzTab-m 2.1.0 released: `engine-mztabm-2.1` becomes a regular module, joins the release, and production gets a `mztab-engine-2-1` service (then drop `ENGINES_UNAVAILABLE_HINT_URL` there). Switching `engines.default-line` to 2.1 follows (spec §11).
