# 2.0.0 deployment and rollout

Prepared, not executed: nothing here has been published, merged or deployed. The project lead or ops carry it out (spec §5.7). The patches below were computed against the current files of `docker-recipes-external` and `lipidcompass-ansible` (read-only checkouts, 2026-10-23).

## Rollout order

1. **Publish the snapshot image.** Trigger the existing `workflow_dispatch` of `.github/workflows/maven.yml` on branch `feat/validator-spa` (GitHub Actions, "Run workflow", branch `feat/validator-spa`). It pushes `docker.lifs-tools.org/lifs/mztab-validator-webapp:2.0.0-SNAPSHOT` (version tag only, never `latest`).
2. **-dev first.** Merge the `-dev` compose patch (below) and redeploy `mztabvalidator-dev`. The volume `mztabvalidator-dev-data` is already mounted at `/tmp/upload-dir/`, which is the default `storage.location` (`${java.io.tmpdir}/upload-dir`), so no environment change is needed.
3. **Parity checklist on `/mztabvalidator-dev`.** Work through `docs/superpowers/plans/2026-10-23-validator-spa-m1-parity.md`, using the real files of the standalone design §3.3 (including the 32 MB file with the 846 x 1,990 table; page through Summary and shift the column window in Chrome). Only a complete checklist allows the next step.
4. **Release 2.0.0** (project lead): merge `feat/validator-spa` into `master`, release with the existing `release` profile so that `lifs/mztab-validator-webapp:2.0.0` is published.
5. **Production.** Merge the production compose patch (image `2.0.0`, `replicas: 1`; the sticky-cookie labels may stay) and redeploy `mztabvalidator`. Keep `replicas: 1`: results are local to an instance.
6. **LipidCompass.** Merge the lipidcompass-ansible volume patch. LipidCompass stays on the 1.0.x image until it opts in to 2.0.0; the volume is harmless for the old image.

## Environment check

No environment change is needed for the new image. `storage.location` defaults to `${java.io.tmpdir}/upload-dir` (`/tmp/upload-dir` in the container), which is where both public stacks mount their volume today. New optional settings (`storage.max-total-bytes`, `sections.cache.max-bytes`, `validation.custom-mappings.enabled`, `rest.synchronous.max-concurrent`, `rest.synchronous.wait`, `matomo.tracker-base`) have defaults; see `docs/self-hosting/configuration.md`. The container memory limit of 2048M is kept. The image starts the JVM with `-XX:MaxRAMPercentage=75` (Jib `jvmFlags` and the `Dockerfile` `ENTRYPOINT`), so the heap is sized from that limit (about 1.5 GB) rather than the JVM's default of a quarter of it; the section cache keeps its 256 MiB default (`sections.cache.max-bytes`). A compose `entrypoint:` override replaces this flag, so add it there if one is used. Watch `docker stats` during the parity check on -dev (see the parity checklist).

## Patch 3: `lipidcompass-ansible` named volume for `mztabvalidator`

The `mztabvalidator` service in `roles/lipidcompass/templates/docker-compose-lipidcompass-infra.yml.j2` has no volume today, so its results would be lost on every redeploy. The patch adds a bind-backed named volume (same pattern as `lc-prod-minio-1` in the data-infra stack) and points `storage.location` at its mount path. The host directory `/var/data/lipidcompass/mztabvalidator` must exist on the swarm node before deployment (a bind mount with `type: none` does not create it). The commented-out example `volumes:` block at the end of the file is replaced by a real `volumes:` key; the commented `lc-prod-configuration` entry below it stays commented.

## Notes

- The `lipidcompass-ansible` service keeps `replicas: 1` and the image tag `1.0.30-SNAPSHOT`; changing it to 2.0.0 is LipidCompass's own opt-in.
- Rollback: set the images back to the 1.0.x tags (and `replicas: 2` for production). **Rolling back loses all stored 2.0.0 results:** 1.0.x calls `storageService.deleteAll()` on startup, which wipes the whole storage volume. Result links shared during the 2.0.0 period stop working.
