# mzTab-M Validator 2.0.0

## Highlights

- **New user interface.** The Thymeleaf pages are replaced by an Angular single-page application in the LIFS design: validator form with progress state, result page with messages, metadata, summary (SML), features (SMF) and evidence (SME) tabs, examples, documentation and not-found pages, retention notice, LIFS branding and Matomo with consent.
- **mzTab 1.0 is retired.** The validator handles mzTab-M only. Use a 1.0.x release for mzTab 1.0 files.
- **mzTab-M 2.1 on the development validator.** <https://apps.lifs-tools.org/mztabvalidator-dev/> also validates mzTab-M 2.1 (`2.1.0-M`) files, with jmzTab-m 2.1 and its own default rules. The production validator handles mzTab-M 2.0; a 2.1 file there gets one error message that points to the development validator. 2.1 joins the releases once jmzTab-m 2.1.0 is released.
- **One validation engine per mzTab-M version.** Each version is validated by the reference implementation of that version: mzTab-M 2.0 by jmzTab-m 1.0.x, mzTab-M 2.1 by jmzTab-m 2.1.x. They run as separate services next to the webapp (see [Deployment](#deployment)); the webapp reads the declared `mzTab-version` of an upload and sends it to the matching engine. A file without `mzTab-version` goes to the engine of the default version (`engines.default-line`, 2.0).
- **Validation profiles and custom mapping files.** Choose a profile from the catalog or upload your own CV mapping file (server option `validation.custom-mappings.enabled`). Profiles belong to mzTab-M versions: `mztab-m-2.0-default` (versions 1.0.0 and 1.1.0) for 2.0 files, `mztab-m-2.1-default` 1.0.0 for 2.1 files. The form offers only the profiles of the file's version, and a profile of another version is rejected. A custom mapping file is used for any version.
- **Results persist.** Results are stored on disk for the retention period (`minCleanupAge`, 7 days by default) and survive restarts and redeploys. A storage cap (`storage.max-total-bytes`) refuses new validations when reached.
- **Checks of the editor have their own pool.** A check of a working copy no longer shares threads with the validation of uploads, so editing a file does not delay anyone else. The pool is bounded (`workingcopy.runs.threads`, `workingcopy.runs.queue`, see `docs/self-hosting/configuration.md`); when its queue is full a check answers 503 with `Retry-After`, and the editor shows the message and asks again by itself.
- **Large files.** The result page pages through tables on the server (checked with a 31 MB file whose SML table has 846 rows by 1,989 columns, 1,990 fields with the row prefix); the browser never receives a whole table.

## Fix a file in the browser

- **Fix this file.** The result page and the start page ("Open a file to fix") open an editor on a copy of the upload, at `/edit/{id}`. Your original is never changed. Everything is a change to the text of the copy, and the engines check the text again; the webapp does not parse or validate mzTab-M itself.
- **Edit in place.** Cells of the tables and values of the metadata are edited in the page (Enter saves, Escape cancels). A line that cannot be read as metadata or as a table row, or a table row with more or fewer cells than its header, opens in a raw line editor, with tabs shown as arrows; "Edit this line as text" opens the line of any message there. Undo and redo (buttons, Ctrl+Z, Ctrl+Shift+Z) keep the last 100 steps.
- **Select a message, see its element.** Choosing a message or an occurrence in the editor opens, marks and scrolls to its metadata entry, table row, cell or column; a new choice clears the previous mark. A message with a line but no element offers "Edit this line as text".
- **Remove a metadata line.** Every metadata entry has a "Remove this line" button; Undo brings the line back.
- **Line numbers stay right.** An edit based on lines that have since moved, because a removal, an undo or redo came first, or a save was refused because the copy had changed, is refused instead of applied to the line that now has that number; the document is reloaded and the editor says so. Afterwards "Edit this line as text" goes and a line open as text is closed; text typed into it that was not saved, or whose save was refused, is kept in a notice. Edit a copy in one tab at a time: changes made in a second tab at the same moment are not always noticed this way.
- **A cell edit cannot land in a moved column.** The editor counts a deleted, inserted or merged column, split cells and a replaced line as changes of the layout, like a moved line: a table page read before one is refused instead of edited, and the document is reloaded. A table's cells cannot be edited while it reloads, or after the reload failed (Retry reads it again). The server refuses an edit of a cell when the column no longer has the header name the page showed (409).
- **Quick fixes with a preview.** Remove a field or column the profile has no section for (Info-2057; for a numbered field such as `database`, all of its lines), remove an empty parameter, write a DOI as `doi:10.xxxx/yyyy`, join a broken line, split a metadata line at its spaces, add a missing mandatory column, add a missing metadata line, remove an unused controlled vocabulary entry. Each shows the before and after of every changed line, and none picks a term, a unit or a value for you.
- **Duplicate columns.** A table with two columns of the same name marks them. "Resolve duplicate column" keeps one column and deletes the others, or merges them into one (the preferred column's value, else the first value of the others that is neither empty nor `null`). No edit may create a repeated column name; the server refuses it (Error-2062 reports a repeated name in a file).
- **A reopened copy is checked again.** If you leave the editor, or the server restarts, before the check of your last change has ended, opening the copy again checks its structure again (never the CV rules, which are checked on request only) instead of showing "Checking your latest changes…" for good. CV messages of an earlier CV check stay shown; if they are of the current text, the status line says they are from an earlier session.
- **Checked as you work.** The structure is checked again after 1.5 seconds without a change, and the new and fixed messages are marked. The rules for controlled vocabulary terms run on demand ("Check CV rules"). When jmzTab-m cannot read on from a line, the editor says "jmzTab-m stopped reading at line N" and that problems below it are not yet reported.
- **CV messages are kept until the next CV check.** A copy of a validation with a profile opens without false "New" marks: its first, structural check is compared with the upload's messages without the CV ones, and the upload's CV messages stay shown. A structural check never removes the CV messages of the last CV check or counts them as fixed; a CV check compares its CV messages with those before it. The status line says "CV rules checked at revision n" or "CV rules not checked since your last change", and the copy's report says which check its CV messages are of, with that check's line numbers. While CV messages kept from an earlier CV check are the only errors left, JSON is not offered and the note says which check they come from; "Check CV rules" checks them again. A CV check that cannot check the rules (the file cannot be read into a model, or the check breaks) is not counted as one: the CV messages of the last CV check stay, and the editor says why (`validation.cvNotChecked`). The engines mark that message with the code `cv_not_checked` (category `cross_check`); before, the message of a broken check had the category `format` and no code. "Check CV rules" pressed during the wait after a change, or while its request waits to be asked again after a busy answer, is no longer replaced by the structural check (also not on the server, for a request made while a check runs). `GET /working-copies/{id}` has the new field `cvCheckedRevision` (the revision of the last CV check; 0 for the upload's validation; null if none).
- **Guidance and a resolution report.** Every message group has guidance: what it means, how to fix it in the tool that wrote the file, and what you can do in the editor. "Download resolution report" saves it as Markdown (`<file>-problems.md`). The Documentation menu in the app bar leads to the common problems (`/docs/problems`) and to "Fixing a file" (`/docs/fixing`), which explains the editor (see [Documentation](#documentation)).
- **Downloads.** The corrected file as `.mzTab`, as JSON (only when the file checks without errors), the original, and two resolution reports: the result page's describes the upload (with its line numbers), the editor's "Download report" describes the last check of the corrected copy (`GET /working-copies/{id}/report?format=md`, with the copy's line numbers and a header that names the revision checked; if the copy has changed since, the header says so). A copy that has never been checked has no report (409). A file that is not UTF-8 can be re-encoded from Windows-1252.
- **Working copies in the REST API.** `/rest/v2/working-copies` creates, edits (at most 5,000 operations per request), undoes, redoes, validates, reads and downloads a copy. A copy is found only by its id; there is no listing. `/validate`, `/validatePlain`, `/convert` and `/convertPlain` are unchanged.
- **Self-hosting.** A copy is one SQLite file in the result's directory (`sqlite-jdbc`, natives bundled; a glibc image is needed), kept `minCleanupAge` days after its last change and counted against `storage.max-total-bytes`. Creating one needs about three times the upload size free. The editor opens files of up to 2,000,000 lines with up to 20,000 cells a line (larger ones answer 422 `too_large`). See `docs/self-hosting/configuration.md` and `operating.md`.
- **Large files.** Measured on a generated file of 31 MB (846 SML rows of 1,990 columns, 1,521 assays, 5,540 metadata lines): creating the copy takes under a second, a page read about 100 ms, a one-cell edit under 100 ms and a column inserted in all rows about a second. See the design document, section 9.

## Linked, grouped validation messages

- **Grouped by rule, fix first.** The Messages tab groups messages of the same rule and leads each group with the suggested fix; the original diagnosis stays underneath. A flat list is one click away.
- **Links into the document.** Each occurrence links to its place: the metadata entry (or metadata group), the table row, cell or column of the summary, features or evidence table. "Highlight all" marks every occurrence of a group.
- **Side by side on wide screens.** From 1100 px the messages sit next to the document, with a stepper to move through the occurrences of a group. On narrow screens the jump opens the tab and a "Back to message" bar returns.
- **CSV report.** New columns `suggestion,rule_id,section,row,column,metadata_key,metadata_group` (`row` is 1-based). The `code` column is now escaped like the other text columns.
- **Metadata endpoint.** `GET /validations/{id}/metadata/{group}` accepts an optional `key` and returns the page that contains it.
- Info-2057 (a field or column the declared profile has no section for) is reported by jmzTab-m without a line or a location. The engines now fill both in when the name the message quotes is exactly one metadata key or one column of a table's first header line, so the message links to its place; a name of a group of numbered fields, such as `database` (`database[1]`, `database[1]-prefix`, ...) or `id_confidence_measure`, links to the group's first line. A name that is not found, or found more than once, is left as reported. The webapp still does not parse mzTab-M.
- Semantic "term not allowed" messages now appear once per element.
- Semantic validation messages are capped at the maximum number of messages, like the structural ones; when some were dropped, an info message says how many.
- When errors prevent reading a file's content, semantic validation is skipped with an info message, instead of reporting "Semantic validation failed … mzTabFile is null".
- An undefined CV label is reported once, where the parameter is defined (jmzTab-m reported it twice, and again for every reference to the parameter). Files whose data lines have only warnings or infos are now read and shown (jmzTab-m dropped their content at level Info).
- Requires jmzTab-m 1.0.8 (adds suggestions, rule ids and locations to validation messages). Old stored results still display; they have no links.

## Versions and validation rules

- **The result names the engine.** The validation result (`GET /rest/v2/validations/{id}`) has two new fields: `engine`, the engine that validated the file (e.g. `mzTab-M 2.0 · jmzTab-m 1.0.8 (build …)`), and `defaultVersionApplied`, true when the file declared no `mzTab-version` and went to the engine of the default version. The result page shows both ("default version"). The `mzTabVersion` field stays.
- **A file without `mzTab-version` is reported, not assumed.** Such a file, TSV or JSON, gets Error-2008 (missing `mzTab-version`), and is not validated as if it declared 2.0. The default version only decides which engine runs the other checks; the result shows "default version" (`defaultVersionApplied`).
- **New default rules for mzTab-M 2.0: `mztab-m-2.0-default` 1.1.0.** It is the mapping bundled with jmzTab-m 1.0.8. Unlike 1.0.0, it no longer reports the two MS:1002887 quantification unit errors. Version 1.0.0 stays in the catalog and can still be chosen.
- **The default rules of mzTab-M 2.1: `mztab-m-2.1-default` 1.0.0**, the mapping bundled with jmzTab-m 2.1. `/validate?semanticValidation=true` uses the default rules of the file's version.
- **Mapping files can be downloaded.** `GET /rest/v2/validation-profiles/{id}/{version}/mapping` returns the CV mapping file of a profile version (XML, as an attachment). `GET /rest/v2/validation-profiles` lists only the profiles of the versions this instance can validate, and takes an optional `mzTabVersion` filter.

## REST API

- `POST /rest/v2/validate` and `POST /rest/v2/validatePlain` keep their parameters and results (including the `semanticValidation=false` default). What changed:
  - `/validate` takes JSON only. XML was listed but never worked (it answered 400); it now answers 415. Unreadable JSON answers 400 with the parser's reason, and so does JSON that is not an mzTab-M model.
  - Errors are JSON `ErrorResponse` bodies, as on the other endpoints. An unknown `level` answers 400 instead of 500.
  - A `maxErrors` outside 0 to 500 answers 400. Before, any value was passed on.
  - A file of an mzTab-M version this instance has no engine for answers 422 with one error message naming the version (and, where configured, the validator that supports it).
- **The "JSON could not be read" validation message has the code `json_not_read`.** Its code was empty before; the CSV report shows it in the `code` column.
- **The validator's message that the CV rules were not checked has the code `cv_not_checked`.** This is the "Semantic validation failed …" error (the mapping could not be loaded, or the check broke) and the "Semantic validation was skipped …" note (the file could not be read into a model). Both now have the category `cross_check` and the code `cv_not_checked`, in the results of `/validate`, `/validatePlain` and `/validations/{id}`, on the result page and in the CSV report (`category` and `code` columns). Before, both had an empty code, and the failed one had the category `format`.
- The `timestamp` of JSON error bodies is the time of the error as an ISO-8601 string (e.g. `2026-10-26T09:41:00.123Z`). It was a number without meaning (`System.nanoTime()`).
- **Limits for the synchronous endpoints** (`/validate`, `/validatePlain`, `/convert`, `/convertPlain`). They work on the request thread, so:
  - They take files up to the upload limit (`spring.servlet.multipart.max-file-size`, 64 MB); larger ones answer 413. Before, `/validate` and `/validatePlain` read a body of any size into memory.
  - At most `rest.synchronous.max-concurrent` of them run at once (default: the number of processors). A request that finds no free slot within `rest.synchronous.wait` (default 10 s) answers 503 with `Retry-After`.
- **Conversion works (#71).** Before, both endpoints answered 501, and their media types were the wrong way round:
  - `POST /rest/v2/convertPlain` takes tab separated mzTab-M (`text/tab-separated-values` or `text/plain`) and returns its JSON representation.
  - `POST /rest/v2/convert` takes the JSON representation and returns tab separated mzTab-M. By default the written file is parsed again; `validate=false` skips that. Comment lines are not written (jmzTab-m's writer does not write them).
  - `/convert` writes the version the model declares. It no longer invents `mzTab-version 2.0.0-M` for a model without one: with `validate=false` the written file has no `mzTab-version` line, with `validate=true` (the default) the conversion answers 422 with Error-2008.
  - A conversion that fails answers 422 with its errors as a JSON list of validation messages. Warnings and infos do not stop a conversion and are not returned; use the validate endpoints for them. Unreadable JSON is 400.
  - XML is no longer listed: it was never implemented.
- New endpoints under `/rest/v2`:
  - `POST /validations` (multipart; level, max errors, validation profile or custom mapping file) starts an asynchronous validation; semantic validation runs when a profile or mapping file is given. The file may be tab separated mzTab-M or its JSON representation;
  - `GET /validations/{id}` status and messages; `DELETE /validations/{id}` deletes the result;
  - `GET /validations/{id}/report` downloads the report;
  - `GET /validations/{id}/metadata` and `/metadata/{group}` read the metadata groups;
  - `GET /validations/{id}/tables/{section}` (sml, smf, sme) with `page`, `size`, `sort`, `descending`, `columns` and `filter`;
  - `GET /validation-profiles` lists the validation profiles;
  - `GET /examples` lists examples; `POST /examples/{id}/validations` validates one; `GET /examples/{id}/content` and `GET /examples/{id}/tour` serve the file and the step list of a bundled example;
  - `GET /app-info` version, build, retention, upload limit and analytics settings, and the validation engines.
- **`/app-info` lists the engines.** The field `engines` (one entry per mzTab-M version: `line`, `mzTabVersions`, `jmztabmVersion`, `available`), `defaultLine` and `unavailableHintUrl` replace the single `jmztabmVersion` field.
- **OpenAPI: the mzTab-M model has one schema per version.** The bodies of `/validate`, `/convert` and `/convertPlain` are `anyOf` `MzTab_2_0` and `MzTab_2_1`, taken from the OpenAPI documents of jmzTab-m 1.0.x and 2.1.x. Nothing changes on the wire, but clients generated from the OpenAPI document see new type names (`MzTab_2_0` and so on instead of `MzTab`, and the model types of each version under their own names).
- **`SetCell` has an optional field `header`.** In `POST /working-copies/{id}/edits`, `{"op": "SetCell", "line": 5, "cell": 3, "text": "x", "header": "name"}` is refused with 409 when cell 3 of the header line of that row's table (SMH, SFH or SEH; the first one if there are several) does not hold `name`, because the columns changed since the caller read the page. An empty header, one with a tab or line break, or a line that is no table row answers 400. A column whose header cell is empty cannot be protected this way (the editor sends no `header` for it); a row whose table has no header line any more is refused with 409 as well. Requests without `header` behave as before.
- **`validation.messagesRevision` in `GET /working-copies/{id}`.** The revision whose text the line numbers of `validation.messages` are of: the revision of the run once it has ended, and, while a run is `RUNNING` (its `revision` is the one being checked), the revision of the earlier run whose messages are still listed. CV messages kept by a structural check are of `cvCheckedRevision` instead. A client that acts on a line named by a message sends this revision as `readAt`/`revision`, so that an edit made after lines moved is refused with 409. The editor does this for "Edit this line as text": after a line was removed above a message's line, it says that the lines changed and does not open the moved line. The field is additive. `GET /working-copies/{id}` also has `layoutRevision`: the revision produced by the last change after which lines or columns may have moved (a line or column edit, a raw line, an undo or a redo; 0 if none), so a client that reads the copy anew knows which line numbers it read earlier are outdated. A quick fix for a CV message kept from an older CV check answers 409 ("Check the CV rules again first"). In the editor, showing such a message after lines moved marks no row or cell and says so.
- **A saved edit is never reported as failed.** The retention stamp of a copy is written in the transaction of the edit, undo or redo, and what follows the commit (restarting retention) can no longer turn a committed change into an error response. If an answer is lost or a request ends with a 5xx, the editor reads the copy again before it says anything: when the copy names the change (`lastChangeId`) as its last, the change counts as saved and the next one is not refused with 409.
- **`changeId` and `lastChangeId`.** `POST /working-copies/{id}/edits` accepts an optional `changeId` (a UUID) in the batch, and `undo` and `redo` an optional query parameter `changeId`; anything else than a UUID answers 400. The copy keeps it, in the transaction of the change, and `GET /working-copies/{id}` (and the answer to a change) has `lastChangeId`: the id of the last edit, undo or redo (null if that one gave none). A client that lost the answer reads the copy and knows from `lastChangeId` whether its change was applied. The editor does this: it never reports a change as failed that was saved, nor as saved one that was not; if another change followed, it reloads and says that the change may or may not have been saved. Requests without `changeId` behave as before. The answer to a change no longer waits for another writer of the copy, and `GET /working-copies/{id}` no longer takes the write lock.
- **`generation`.** `GET /working-copies/{id}` (and the answer to a change) has `generation`: a UUID that names this incarnation of the copy. A copy deleted and created again for the same validation restarts at revision 0 with another generation. `POST /working-copies/{id}/edits` accepts an optional `generation` in the batch, and `undo` and `redo` an optional query parameter `generation`; if it is not the copy's the call answers 409 (anything else than a UUID, 400) and changes nothing (the 409 body has `error: "copy_replaced"`), so a revision of the old copy is never taken for the new one's. Requests without it behave as before. The editor sends it.
- **Unpaired surrogates are refused.** An edit whose text (a cell, a metadata value or key, a raw or inserted line, a column name or header) holds an unpaired UTF-16 surrogate answers 400 and changes nothing; before, it was stored as `?`. Valid pairs (emoji) are stored as they are.
- Errors under `/rest/**` are JSON.

## Deployment

- **Three services instead of one.** The webapp (`lifs/mztab-validator-webapp`, port 8083) and one engine per mzTab-M version: `lifs/mztab-validator-engine-2.0` (port 8084) and `lifs/mztab-validator-engine-2.1` (port 8085), all tagged with the webapp's version. The engines are stateless, need no volume and no authentication, and must be reachable from the webapp only. Release images exist for the webapp and the 2.0 engine; the 2.1 engine is published as a snapshot until jmzTab-m 2.1.0 is released.
- **Configure the engines** with `engines.mztabm[n].line` and `.url` (environment `ENGINES_MZTABM_0_LINE`, `ENGINES_MZTABM_0_URL`, …). The default is one 2.0 engine at `http://mztab-engine-2-0:8084`. The webapp offers only the versions it has an engine for, and does not start if the default version (`engines.default-line`) has none. See `docs/self-hosting/configuration.md`.
- **Memory moves to the engines.** Parsing and validation run in the engines: start with 2048 MB per engine and 1024 MB for the webapp.
- **Health:** `/actuator/health` of the webapp reports each engine as a component (`engines` → `engine-2-0`, `engine-2-1`). An engine that is down shows as `UNAVAILABLE` and does not take the webapp down; that version's validations then fail with "The mzTab-M 2.1 validator is temporarily unavailable. Please try again later."
- **The engines' OLS endpoint is configurable** with `engine.ols.protocol`, `engine.ols.host` and `engine.ols.base-path` (defaults: the EBI OLS, `https://www.ebi.ac.uk/ols`).

## Upgrade notes

- **One replica per instance.** Results live on the instance's local storage. The production stack goes from two replicas to one.
- **Mount a volume at `storage.location`** (default `${java.io.tmpdir}/upload-dir`, i.e. `/tmp/upload-dir` in the Docker image) to keep results across redeploys. For the storage volume, compose files that already mount it at `/tmp/upload-dir` need no environment change. The stack itself does change: it needs the engine services, a network the webapp shares with them, and `ENGINES_*` settings wherever the engines differ from the default (one 2.0 engine at `http://mztab-engine-2-0:8084`); see Deployment above.
- Server-side analytics events are anonymous. Browser analytics (Matomo) load only if `ga.id` is set and only after consent.
- Old URLs keep working: `/validate/{id}` redirects to `/result/{id}`; `/validate/{id}/delete` opens the result page with the delete confirmation (it never deletes on GET).
- The Docker images are published as `lifs/mztab-validator-webapp`, `lifs/mztab-validator-engine-2.0` and `lifs/mztab-validator-engine-2.1`. They start the JVM with `-XX:MaxRAMPercentage=75`, so the heap follows the container memory limit.
- Add at least the 2.0 engine next to the webapp; without a reachable engine no file can be validated. The webapp itself no longer contains jmzTab-m or talks to the EBI OLS; the engines do.
- **Copies of results stored before this version.** A result validated before the deploy keeps its messages as they were stored, without the code `cv_not_checked`. A corrected copy made from it after the deploy does not know that its CV rules were not checked:
  - an old "Semantic validation failed …" error (category `format`) counts as a structural message, and the copy's first check may list it once as "Fixed";
  - an old "Semantic validation was skipped …" note stays listed as a CV message of revision 0 until **Check CV rules**.

  Validating the upload again avoids both.
- Rolling back to 1.0.x deletes all stored 2.0.0 results: 1.0.x empties the storage directory on startup.
- The Thymeleaf, jQuery, Bootstrap and mzTab 1.0 dependencies are removed.
