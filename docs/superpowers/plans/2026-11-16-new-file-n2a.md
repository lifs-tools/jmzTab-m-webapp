# New File and the Import Pipeline (N-2a) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A researcher chooses **New file**, gets a working copy that validates from the first moment, sees what the repository rules still miss, and fills the copy from a vocabulary file. The import is previewed first and applied as one undoable edit.

**Architecture:** The engines get two operations: **skeleton** and **field rules**. `mappings/apply` gains `keepExisting` and an `InsertLines` edit. The webapp gets three things:
- new copies, which keep their settings in the copy's own meta and have no validation session;
- an imports endpoint, which runs the copy's output mapping in the engine and returns a preview with an `EditBatch`, as a quick fix does;
- a "still missing" endpoint.

The SPA gets the `new` route, and the library gets an **Add from…** panel with the import preview and the "still missing" checklist. The webapp still reads no mzTab-M beyond the version line.

**Tech Stack:** Java 24, Spring Boot, Jackson, jmzTab-m 1.0.8 (2.0 engine) and 2.1.0-SNAPSHOT (2.1 engine), SQLite working copies, Angular 21 with signals, Vitest, Playwright.

**Spec:** `docs/superpowers/specs/2026-11-08-new-mztabm-file-design.md`, chiefly §2 Goal 1, §4 (N7, N8, N9, N11, N12, N18), §5.1 journey 1, §5.7, §5.10, §5.11 and §6 N-2. The editor design `2026-10-31-mztabm-editor-design.md` §5.2–§5.4 and §5.9 describe the working copies this builds on. Read both before any task.

## Where N-2 is split

Design §6 N-2 has several separate subsystems. It is built as three plans, each shipping on its own:

| Plan | Scope | Done when |
|---|---|---|
| **N-2a (this plan)** | `InsertLines`; skeleton; new copies; the New-file route; field rules and "still missing"; the imports endpoint and the Add-from panel, with one input kind: a vocabulary file (JSON). | A new 2.0 file, filled from `examples/v3-example/instance.json` dataset 1, has no errors under `mztab-m-2.0-default`. Undo removes the whole import in one step. |

## Decisions this plan makes

These go into the design as an amendment in Task 1.

- **D1, the §5.7 entry criterion: an `InsertLines(before, lines)` operation** in engine-api (`LineEdit`) and the server (`EditOperation`). It counts as one operation. The applier emits consecutive new lines as one `InsertLines`. A cap on the size of a mapping batch is rejected, because a 300-sample, 3,000-lipid study is the real case. [my call]
- **D2, the skeleton holds only what the researcher chose:** `mzTab-version`, `mzTab-ID` and, for 2.1, `mzTab-profile`. It is not a valid file. A valid one needs facts nobody has given yet (polarity, quantification method, runs), and placeholders would be invented data. The validation messages and the "still missing" checklist list the rest. This overrides editor design §5.8's "a minimal valid TSV". [my call]
- **D3, a new copy has no validation session** (§5.10). Its settings live in the copy's meta:
  - `copy.origin` = `new`;
  - the repository rules;
  - the level and error limit;
  - the content profile.

  Upload copies keep reading their session; one `CopySettings` lookup serves both. `createOrFind` returns an existing copy before it looks for a session, so `edit/:id` opens a new copy as it opens any other. [my call]
- **D4, an import answers with a preview that carries an `EditBatch`**, as `QuickFixPreview` does. The SPA applies it through `POST /edits` with its revision, change id and generation, so a conflict, a replaced copy and undo work exactly as for every other change. This drops §5.10's `imports/{importId}/apply` endpoint and any stored import. [my call]
- **D5, an import is applied whole.** One choice decides what happens to existing values: **Keep existing values** (default on) or replace them. With it on, the engine reports a different existing value as `CONFLICTS` and leaves it alone. Per-suggestion ids (§5.10) are not built. Dropping single lines of an element would leave index gaps and dangling references. Per-group acceptance comes with the methods text (N-4), where §5.7 asks for it. [my call]
- **D6, the first input kind is `vocabulary-instance`:** a vocabulary instance as JSON (design §5.2: the v3 reader's output, `examples/v3-example/instance.json`). It needs no input mapping, so `inputMapping` in the provenance is null. Tools that already produce the vocabulary use it directly ("Use the mappings in your tool", §7). [my call]
- **D7, "still missing"** lists the MUST and SHOULD rules of the copy's repository rules that the copy does not meet. The engine decides that from the copy's text (field rules with `present`). The vocabulary's per-repository requirement levels (N14) are not used yet. The catalog has only the default profiles, and the vocabulary has no per-repository levels, so N14's build check has nothing to compare. It comes with the first repository profile. [my call]
- **D8, imports are offered only where an output mapping targets the copy's version.** In N-2a that is 2.0 only; 2.1 gets its mapping in N-2c. The server lists the output mappings it carries. [my call]

## Global Constraints

- **The webapp parses no mzTab-M beyond the version line** (engines design §2, N7). The skeleton, field presence and the mappings run in the engines.
- **Versions offered:** only those whose engine is configured (E13), with `engines.default-version` preselected (N12).
- **Profiles:** a repository-rules profile must list the version (E9). New files take catalog profiles only; no custom mapping upload.
- **Words in the UI** (N11):
  - **mzTab-M version**;
  - **content profile** (2.1 only: `M`, `M+S`, `M+F`, `M+F+E`, `M+S+F+E`);
  - **repository rules** (the validation profile).
- **Caps:**
  - `WorkingCopyEditor.MAX_OPERATIONS` (5,000) is unchanged, and an `InsertLines` counts as one operation;
  - the existing per-line checks (`MAX_LINE`, `CopyText.MAX_CELLS`, well-formed text) and the copy's `CopyText.MAX_LINES` apply to every inserted line;
  - an import's instance is at most 5 MiB (413);
  - a copy whose text exceeds the engine's `maxUploadBytes` gets no import (413).
- **`mzTab-ID` entered on the form:** `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`.
- **Engine API changes** update `engine-api/src/main/resources/engine-openapi.json` (`EngineOpenApiContractTest`).
- **Server API changes:** run `cd frontend && npm run generate:api`.
- **Copyright** of new files: the Apache-2.0 block with "Copyright 2026 LIFS Tools Consortium.", never the ISAS header.
- **Builds:**
  - Maven offline: `./mvnw -B -o -nsu …`;
  - frontend: `cd frontend && npm test`;
  - e2e: as in `docs/self-hosting/building.md`.

  Subagents never run `./mvnw install`.
- **Branch:** `feat/new-file-n2a`, from `origin/master`.

## Review Focus

1. **Reopening a new copy** (reload, second tab, the link from another device): `edit/:id` must open it, not answer "unknown validation". Owned by Task 3: `newCopyReopensWithoutSession`.
2. **An edit between preview and apply.** The batch carries the preview's revision. The server answers 409, the store re-reads the copy, and the panel computes the preview again and says so. Nothing is half-applied. Owned by Task 8: `staleImportIsPreviewedAgain`.
3. **An instance with several datasets, or a dataset index out of range.** The SPA asks which dataset (N9). The server answers 400 with a message naming the range, never 500. Owned by Task 5: `datasetIndexOutOfRangeIs400`, and Task 8: `asksForDatasetWhenSeveral`.
4. **A large import** (3,000 SML rows): one batch of at most a few dozen operations, applied and undone in one step. A batch over the undo budget is refused with a message, and nothing changes. Owned by Task 2: `insertLinesUndoesInOneStep`, `insertLinesOverBudgetRefused`.
5. **The "still missing" checklist of a copy the engine cannot parse.** It says that the rules could not be checked; it never shows an empty "nothing missing". Owned by Task 4: `unparsedTextGivesUnknownPresence`, and Task 6: `stillMissingUnknownWhenNotParsed`.
