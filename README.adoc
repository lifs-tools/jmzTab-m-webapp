Besides validating, the web application helps you fix a file: each problem comes with guidance, and the editor corrects cells, metadata values, broken lines and duplicate columns in the browser, with quick fixes that show a before and after, undo and redo, and a resolution report to take back to the tool that wrote the file. See "Fixing a file" in the application, or `docs/release-notes/2.0.0.md`.

This project provides a validator implementation and web application for the https://github.com/HUPO-PSI/mzTab[mzTab-M standard for metabolomics], versions 2.0 and (on the development validator) 2.1. Each mzTab-M version is validated by the reference implementation of that version, https://github.com/lifs-tools/jmzTab-m[jmzTab-m] 1.0.x for 2.0 and 2.1.x for 2.1, running as a separate engine service next to the web application. Support for mzTab 1.0 (proteomics) was retired in version 2.0.0; please use an earlier 1.0.x release for those files.

== Using the LIFS Web application

The mzTab validator webapplication is hosted https://apps.lifs-tools.org/mztabvalidator[here]. 
For programmatic usage of the validation service, the REST API description is available https://apps.lifs-tools.org/mztabvalidator/swagger-ui.html[here].
The release notes of the current version are in `docs/release-notes/2.0.0.md`.

== Project layout

The build is a Maven reactor:

`server`:: the https://projects.spring.io/spring-boot/[Spring Boot] web application (REST API under `/rest/v2`, persistence of results). It serves the single-page application and sends every file to the engine of its mzTab-M version; it contains no mzTab-M parser itself. Built as an executable JAR and the image `lifs/mztab-validator-webapp` (port 8083).
`frontend`:: the https://angular.dev/[Angular] single-page application with https://material.angular.dev/[Angular Material] in the LIFS design. Maven builds it with a local Node installation and the `server` module packages the result.
`engine-api`:: the contract between the web application and the engines: request and result types and the engine OpenAPI document.
`engine-core-src`:: the engine sources (validation, conversion, section data). Not a module: every engine compiles them against its own jmzTab-m line.
`engine-parent`:: the build the engines share.
`engine-mztabm-2.0`:: the mzTab-M 2.0 engine on jmzTab-m 1.0.x, image `lifs/mztab-validator-engine-2.0` (port 8084).
`engine-mztabm-2.1`:: the mzTab-M 2.1 engine on jmzTab-m 2.1.x, image `lifs/mztab-validator-engine-2.1` (port 8085). It is built by default and left out with `-DskipSnapshotEngines`, as releases do while jmzTab-m 2.1 is a SNAPSHOT.

== Building the project from the command-line

Building all modules, running the unit tests of the engines, the server and the frontend:

  ./mvnw -B verify

For a faster build that skips the Angular build (the SPA is then not part of the JAR):

  ./mvnw -B verify -Dfrontend.skip=true

The packaged applications are `server/target/mztab-validator-webapp-<VERSION>.jar`, `engine-mztabm-2.0/target/mztab-validator-engine-2.0-<VERSION>.jar` and `engine-mztabm-2.1/target/mztab-validator-engine-2.1-<VERSION>.jar`.

A release is built with `./mvnw -B -Prelease -DskipSnapshotEngines …` and fails on any SNAPSHOT dependency; see link:docs/self-hosting/building.md#releases[Building: Releases].

== Running the Web Application for Development

Start both engines and the web application from the packaged JARs, as in production (port 8083, context path `/mztabvalidator`, which the proxy configuration of the frontend expects):

  scripts/run-dev-stack.sh --build

`--build` runs `./mvnw -B package -DskipTests` first; without it the script builds only when a JAR is missing. `--no-21` leaves out the 2.1 engine. The engines log to `target/dev-stack/`; Ctrl-C stops all three. With Docker, `compose/dev-stack.yml` runs the same JARs in containers:

  ./mvnw -B package -DskipTests
  docker compose -f compose/dev-stack.yml up

Then, in a second terminal, start the Angular development server. It proxies `/rest` to `http://localhost:8083/mztabvalidator/rest` on the running server (see `frontend/proxy.conf.json`):

  npm --prefix frontend install
  npm --prefix frontend start

The frontend is then available at http://localhost:4200/ and reloads on changes.

=== End-to-end tests

The Playwright end-to-end tests run against a packaged web application and both engines that are already running (they are not part of `./mvnw verify`). Start them as above (`scripts/run-dev-stack.sh` uses a storage directory below `target/dev-stack/`), then:

  npm --prefix frontend run e2e

`E2E_BASE_URL` overrides the default address `http://localhost:8083/mztabvalidator/` (it must end with a slash).

== Running your own instance

The guide in link:docs/self-hosting/README.md[`docs/self-hosting`] covers building, configuring and operating your own mzTab Validator:

* link:docs/self-hosting/building.md[Building]: prerequisites, the JAR, Docker images.
* link:docs/self-hosting/configuration.md[Configuration]: every setting with its default, validation profiles, analytics, logging.
* link:docs/self-hosting/operating.md[Operating]: the JAR or the container, reverse proxy, storage and retention, memory, monitoring, security, upgrades, troubleshooting.

In short: an instance is the web application plus one engine per mzTab-M version (Java 24 or later, or the three images):

  java -jar engine-mztabm-2.0/target/mztab-validator-engine-2.0-<VERSION>.jar &
  java -jar server/target/mztab-validator-webapp-<VERSION>.jar --storage.location=/var/lib/mztabvalidator \
    "--engines.mztabm[0].line=2.0" "--engines.mztabm[0].url=http://localhost:8084"

serves the application at http://localhost:8083/mztabvalidator, for mzTab-M 2.0 files.

What an instance needs:

* *A persistent directory or volume for the web application's `storage.location`.* Uploads, results and the data of the result page are kept there for `minCleanupAge` days (7). The engines are stateless.
* *One web application instance per storage directory.* Results are files of one instance; do not load-balance several.
* *A private network between the web application and the engines*, which have no authentication.
* *Outbound HTTPS* from the engines to the https://www.ebi.ac.uk/ols4/[EBI Ontology Lookup Service] for semantic validation, and from the web application to `raw.githubusercontent.com` for the example files. Structural validation works offline.
* *A reverse proxy* in front of the web application that forwards `X-Forwarded-*` headers and accepts uploads up to `spring.servlet.multipart.max-file-size` (64 MB).

The project's images are built with Jib (`-Pdocker`) and published as `docker.lifs-tools.org/lifs/mztab-validator-webapp`, `docker.lifs-tools.org/lifs/mztab-validator-engine-2.0` and `docker.lifs-tools.org/lifs/mztab-validator-engine-2.1`. The `docker` profile pushes to a registry during `package`; see link:docs/self-hosting/building.md#docker-images[Building] for local images and for pushing to your own registry.
